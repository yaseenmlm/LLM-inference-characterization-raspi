LLM decode on a Raspberry Pi 5: memory bandwidth as the limit

Yaseen Malam · November 2026 · Source code and data

Abstract

Each token a language model generates reads about every weight once, so decode speed should not exceed read bandwidth divided by model size. I measured read bandwidth on a Raspberry Pi 5, used it to predict a decode ceiling for seven quantized models, and compared the prediction with llama.cpp runs. A Ryzen 7 7700X desktop ran the same workload for comparison. No run exceeded its ceiling (— of —). At 4 threads the Pi reached — of the ceiling. The 7700X reached — at 1 thread but only — at 8, because its decode slowed as threads were added, by a cost per layer that does not depend on model size.

1 Method

Generating one token streams the weights from memory once and does not write them, so the ceiling is

ceiling (tok/s) = read bandwidth (GB/s) ÷ model size (GB)

Read bandwidth comes from a custom read-only test that sums a 1 GiB block, split across threads. I used it rather than STREAM Triad, which also writes and underestimates the ceiling. Model size is the GGUF file size. Prefill and decode were measured in separate llama-bench calls with a 256-token prompt and 128 generated tokens, 3 repeats each. A run counted only if the CPU held its clock throughout. On the Pi that meant 2.4 GHz with no throttle flags, after a cooling test passed.

2 Results

2.1 Read bandwidth

Figure 1 shows the input to the ceiling. The Pi's bandwidth falls as threads are added, which I have not explained. The 7700X's rises from 1 to 2 threads and then stays roughly flat.

2.2 Decode against the ceiling

Figure 2 plots measured decode speed against model size, with the ceiling for the chosen machine and thread count. On log axes the ceiling is a straight line. On the Pi at 4 threads every model sits just below it. On the 7700X the gap widens as threads are added.

2.3 Thread scaling

Adding threads adds compute but not bandwidth, so the shape of each line shows which limit applies. On the Pi, Qwen Q2 is limited by the CPU at low thread counts: it reaches — of its ceiling at 1 thread and nearly doubles at 2. Qwen Q8 is limited by memory from the first thread, at —. On the 7700X, decode is fastest at 1 or 2 threads for 6 of the 7 models.

2.4 The 7700X slowdown

To see where the 7700X loses time, I subtracted the ceiling's predicted time per token from the measured time and divided by the model's layer count (Figure 4). If memory caused the loss, it would grow with model size. It does not: Qwen Q8 is 2.4 times the size of Q2, but at 8 threads both lose — and — ms per layer. The loss grows with thread count instead. The likely cause is threads waiting for each other after each step of a layer, which I have not measured. Qwen 7B loses less, and I have not explained why.

3 Limitations

  • The PC ran Windows with a different compiler, so its thread slowdown may come from that build rather than the 7700X.
  • The ceiling uses GGUF file size, which also includes metadata.
  • Pi temperatures were sampled at about 1 Hz, and the PC had no temperature log, only clock speed.
  • Qwen 7B prefill on the Pi could not be measured without tripping the soft temperature limit.
  • Part of the Pi sweep ran prefill and decode in one call, which moved decode by about 2% in two checks.
